# Ревью classic-migrations 2.1.0

Ревью от 2026-11-04 по ветке `main` (`2657f5b`). Код совпадает с версией 2.1.0 на PyPI.
Проверка: чтение кода, пробы на SQLite и CLI, pyright strict на типичном использовании API.
PostgreSQL во время ревью был недоступен: всё про поведение PG, Oracle, MySQL и MSSQL выведено из кода и помечено «не проверено».

## Замечания к коду

1. **Безусловный импорт `typing_extensions`.** [высокая]
   - Где: `backends/base.py:26`, `migrator.py:27`; зависимость объявлена только для `python_version < '3.11'` (`pyproject.toml:32`).
   - Последствие (проверено): на Python 3.11+ без `typing_extensions` импорт пакета падает с `ModuleNotFoundError`.
     Сейчас работает, только если пакет пришёл транзитивно.

2. **MySQL: `transactional_ddl = True`.** [высокая, не проверено]
   - Где: `backends/pymysql.py:34`.
   - Последствие: в MySQL DDL неявно коммитит транзакцию. При ошибке в середине миграции часть DDL уже применена,
     а история говорит «не применена».

3. **Oracle: нетранзакционный путь не коммитит события истории и DML.** [высокая, не проверено]
   - Где: соединение без autocommit (`backends/oracle.py:68-82`), `transactional_ddl = False`;
     `mark()` и statements в ветке `migrator.py:219-223` вне `TransactionManager` никто не коммитит, `close()` откатывает.
   - Последствие: событие APPLIED последней миграции может потеряться. Тест не ловит: читает историю в том же соединении.

4. **SQLite: весь запуск — одна транзакция.** [средняя]
   - Где: `acquire_lock` = `BEGIN IMMEDIATE` (`backends/sqlite3.py:85-103`), поэтому `TransactionManager` не открывает своих (`base.py:57`).
   - Последствие (проверено): ошибка во второй миграции откатила первую и даже таблицу истории.
     `transactional: false` невозможен (`VACUUM` падает). Хуки идут внутри транзакции — противоречит README.

5. **`target` в apply/rollback считается по позиции в топологическом списке, а не по графу.** [средняя–высокая]
   - Где: `migrations.py:296-301`, `318-328`.
   - Последствие (проверено): `apply 0002.b` применил и независимую `0003.c`; `rollback 0003.c` откатил и независимую `0002.b`.

6. **Порядок независимых миграций не лексикографический.** [средняя]
   - Где: `TopologicalSorter.static_order()`, `migrations.py:252`.
   - Последствие (проверено): порядок `['0001.a', '0003.c', '0002.b']`. Номер в имени файла ничего не гарантирует.

7. **Директивы разбираются молча и хрупко.** [низкая–средняя]
   - Где: `migrations.py:43-63`.
   - `-- Depends:` (другой регистр) и опечатки молча игнорируются (проверено).
   - Две строки `-- depends: a` и `-- depends: b` склеиваются через пробел и дают id `"a b"` → `NoMigration`.

8. **PENDING после сбоя невидим.** [средняя]
   - Где: `migrator.py:219-223`, `245-249`; `applied_ids` смотрит только на APPLIED (`migrations.py:261-270`).
   - Последствие: частично применённая миграция при следующем запуске выполняется с начала. `list` показывает `U`.
     Команды пометить/снять пометку нет.

9. **Несуществующий каталог в `sources` молча даёт пустой список.** [средняя]
   - Где: `migrations.py:201-205`. Последствие (проверено): «Nothing to apply», тесты стартуют без схемы.

10. **`SOURCES` делится по `:`.** [средняя]
    - Где: `settings.py:122`. Последствие (проверено): на Windows `C:\proj\migrations` → `['C', '\\proj\\migrations']`.

11. **`MigrationsCollection` не принимает `Path`.** [низкая]
    - Последствие (проверено): `TypeError: 'WindowsPath' object is not iterable`.

12. **CLI создаёт коллекцию и мигратор в `__init__`, до разбора аргументов.** [средняя]
    - Где: `cli.py:55-56`. Последствие (проверено): `migrations --help` без `SOURCES` падает с `ValueError`.
      Ошибки (`NoMigration`, ошибки БД) выходят трейсбеком.

13. **Жизненный цикл соединения в `Migrator`.** [низкая–средняя]
    - Если `acquire_lock` в `__enter__` падает, соединение не закрывается, `_backend` остаётся заполненным (`migrator.py:84-94`).
    - В `__exit__` нет `try/finally` (`migrator.py:105-110`): сбой `rollback`/`release_lock` скрывает исходную ошибку, `close()` не выполняется.
    - `ensure_migration_table` вызывается дважды за один `history()` (`migrator.py:122`, `base.py:186`).

14. **Разная семантика блокировок между СУБД.** [низкая]
    - PG и MySQL ждут бесконечно, MSSQL и Oracle сразу падают с `MigrationLockError`.
    - Ключ блокировки зависит только от `migration_table`, не от схемы: проекты с разными `migration_schema` блокируют друг друга.

15. **Нельзя передать дополнительные параметры подключения.** [средняя]
    - `Backend` поддерживает `db_args` (`base.py:119`), `Migrator` — нет: не задать `sslmode`, `connect_timeout`, `options`.

16. **PG: autocommit-сессия общая для всех миграций и хуков.** [низкая]
    - Где: `backends/psycopg.py:48`. `SET search_path` из одной миграции влияет на следующие.

17. **Rollback без `.rollback.sql` молча пишет ROLLED_BACK** (лог debug, `migrator.py:227-233`). [низкая–средняя]

18. **`rollback_path` — `name.replace(".sql", ".rollback.sql")`** заменяет все вхождения; `*.SQL` молча игнорируются (`migrations.py:163`). [низкая]

19. **Безопасность.** [низкая]
    - MSSQL: имя схемы внутри строкового литерала `EXEC('CREATE SCHEMA "..."')` (`backends/pymssql.py:54-55`).
    - `BadConnectionURI` кидается при неизвестном драйвере (`base.py:108`) — имя вводит в заблуждение.
    - Парсер `.env` (`settings.py:22-35`) не снимает кавычки и не понимает inline-комментарии.

20. **Схемы.** [информация]
    - PG и MSSQL сами создают `migration_schema` (`backends/psycopg.py:66-73`, `backends/pymssql.py:50-58`), Oracle — нет.
    - Схему объектов приложения библиотека не создаёт и `search_path` не меняет — это делает миграция.
    - Если `migration_schema` совпадает со схемой модуля, `CREATE SCHEMA <module>` в первой миграции падает.

21. **Мёртвый код.** [низкая]
    - `InvalidArgument` нигде не бросается — ветка `except` в `cli.py:242` мёртвая.
    - `disable_transactions` (`base.py:262`, `psycopg.py:122`, `sqlite3.py:105`) не вызывается; `ALL_STATUSES` (`base.py:33`) не используется.
    - Атрибут класса `versions_table` перекрывается в `__init__`.
    - `pyproject.toml:83,96` исключает несуществующий `backends/contrib`.

22. **Версии.** `__version__ = "2.0.0"` (`__init__.py:31`) при пакете 2.1.0; в CHANGELOG нет 2.1.0, 2.0.0 помечен «unreleased». [низкая]

23. **Типизация.** [низкая]
    - `Migration` и `Hook` возвращаются публичным API, но не экспортированы.
    - `history()` → `list[tuple[Any, ...]]`, `Backend` почти весь на `Any`, хуки — `dict[str, list[Hook]]` со строковыми ключами.
    - Несогласованные имена: `db_pass` / `DATABASE_PASSWORD` / `Backend(db_password=...)`; `versions_schema` / `OLD_MIGRATIONS_SCHEMA`.

24. **Мусор в локальном клоне** (не в репозитории): `build/`, `dist/`, папки с `__pycache__` от старой структуры
    (`backends/contrib`, `backends/core`, `scripts`), `egg-info`; незакоммиченные `example/*.sql`.

## Замечания к документации

- Уровни `-v` неверны: README.rst:189-190 — по умолчанию ERROR, `-v` → WARNING…; в коде (`cli.py:29-33`) по умолчанию WARNING, `-v` → INFO, `-vv` → DEBUG.
- CHANGELOG:12-21 упоминает несуществующий `Migrator.lock()`.
- README.rst:161-163 противоречит сам себе про `transactional` (по умолчанию `true` / «определяется СУБД»).
- README.rst:172-174 «хуки всегда вне транзакции» — на SQLite не так.
- `Settings` экспортируется, но не указан в списке публичного API (README.rst:244-254).
- Нет разделов:
  - схемы (п. 20);
  - порядок и зависимости: порядок не лексикографический, нужна цепочка `depends`; смысл `target`;
  - правила имён файлов: id — имя без `.sql`, регистр расширения, дубликаты id → `MigrationConflict`,
    зарезервированные имена хуков, rollback-файл без основного игнорируется, glob в `sources`;
  - сбои и PENDING, особенности MySQL и SQLite;
  - рецепты: программный запуск из pytest с teardown, откат до конкретной миграции, `python -m classic.migrations`, коды выхода;
  - формат `.env`, разделитель `SOURCES`, таймауты блокировок по СУБД.
- AGENTS.md: версия 2.0.0, упоминает «вызовы `cmd_*`» в test_cli (теперь методы `CLI._apply` и т.п.).

### Решения (2026-11-04)

- Ветка `v3`, следующая версия 3.0.0. Сначала инфраструктура, затем исправления, mutmut, документация.
- Проверки выполняются на pull request до слияния; в `main` код попадает только через PR с обязательным
  чеком `All checks` (защита ветки настраивается на GitHub). `publish.yml` проверки не повторяет.
- `target` считается по графу: `apply X` — X и её зависимости, `rollback X` — X и зависящие от неё.
- Миграция в статусе PENDING блокирует `apply`/`rollback`, пока пометку не снимут вручную; `list` показывает её.
