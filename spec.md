## Migration
У миграции есть директивы, вычитываемые из комментариев в начале .sql файлов.

Директива depends принимает названия других миграций, перечисленные через запятую. Пробелы между названиями должны обрезаться. Названия миграций должны совпадать с реальными, иначе должно явно выкидываться исключение NoMigration.

Директива transactional принимает значения "true" или "false", и None, если не указано.

Каждая миграция с transactional=True оборачивается в свою транзакцию, также в этой же транзакции происходит запись в историю миграций с пометкой 'APPLIED'.

Миграции с transcational=False применяются  в режиме autocommit, запись в историю миграций производится сначала перед применением с пометкой 'PENDING', затем после успешного применения с пометкой 'APPLIED'.

При применении миграции с transactional=None поведение берется от БД - если БД поддерживает Transactional DDL, то миграция оборачивается в транзакцию, иначе - нет.

Также для каждой миграции есть возможность указать rollback-миграцию. Такая миграция должна размещаться рядом с самой миграцией, и иметь название <название основной>.rollback.sql. У таких миграций есть только директива transactional. Поведение transactional аналогичное основной миграции.

## Hook
Hook - это просто набор SQL-statement, выполняемых в начале или конце миграции/rollback, без директив.

Hook всегда применяется вне транзакции.

## История миграций
Таблица с историей миграций в БД должна содержать столбцы:
- created_at: дата и время записи
- migration_id: название миграции
- status: строка со значением 'PENDING', 'APPLIED' и 'ROLLED_BACK'.

## MigrationsCollection
Класс Migrations теперь должен называться MigrationsCollection. Конструктор принимает только путь к каталогу миграций (или список путей); коллекция не имеет доступа к БД.
Его публичные методы:
- list. Возвращает список миграций, отсортированный топологически. 
- to_apply. Принимает историю миграций (лог событий от Migrator.history()), по ней вычисляет применённые миграции и возвращает кортеж (hooks, migrations): хуки и список неприменённых миграций, отсортированный топологически. Также может принимать аргумент target: str - название миграции, если указан, возвращает миграции до указанной включительно.
- to_rollback. Аналогично to_apply, только для rollback: возвращает хуки и список применённых миграций в обратном топологическом порядке, до target включительно.

## Migrator
Появляется новый класс Migrator. Этот класс принимает параметры для БД, выбирает Backend для указанного драйвера, использует backend для доступа к реальной БД. Не должен содержать SQL напрямую. Драйвер задаётся именем модуля драйвера (например, 'sqlite3', 'psycopg').
Публичные методы:
- lock. Берет advisory lock через бекенд, возвращает контекстный менеджер. Полученный lock передаётся в остальные методы Migrator, чтобы методы могли проверить наличие блокировки через assert lock.is_acquired.
- history. Принимает lock, возвращает историю миграций - лог событий таблицы истории.
- apply. Принимает lock, hooks и список Migration, применяет их в указанном порядке. Имеет параметр fake: bool, при True только создает записи в истории миграций - без выполнения SQL миграций и без запуска хуков. Перед применением запускает hook pre-apply, после - post-apply.
- rollback. Аналогично apply, только откатывает миграции: при указанном migration_name откатывает миграции до указанной включительно. Хуки - pre-rollback и post-rollback. При fake=True также только создает записи в истории.

В тестах нужно создать FakeBackend, и подсунуть его для тестирования Migrator.
FakeBackend может содержать состояние с якобы примененными миграциями и методы для проверки состояния в тестах.

## Backends
Класс DatabaseBackend переименовывается в Backend. Содержит базовую логику для всех бекендов, но не содержит SQL - это должно быть в реализации бекендов.

Бекенды не являются публичными объектами, они используются внутри Migrator.

Тесты каждой имплементации Backend должны обращаться к реальной БД.

## CLI
В командах CLI должны остаться только:
- list c опцией --history. Выводит список миграций с их статусом в текущей БД, при ключе --history - только примененные миграции.
- apply. Применяет миграции. Если указан ключ --fake - только создает записи в истории. При указанном ключе --plan не применяет миграции, а только выводит список тех, которые можно применить к текущей БД. Имеет позиционный необязательный аргумент migration_name, если указано - применяет миграции до указанного name включительно, если нет - то все доступные.
- rollback. Аналогично apply, только откатывает миграции: при указанном migration_name откатывает миграции до указанного включительно.

В тестах cli должен использовать mock вместо реального объекта Migrator. Цель теста - убедиться, что CLI правильно парсит аргументы и передает в соответсвующие методы.

## Public API
Библиотека должна давать примерно такой публичный API (например, для запуска миграций при тестировании проектов):

db = Migrator(
    driver='psycopg',
    db_host='localhost',
    db_port='5432',
    db_name='tests',
    db_user='test',
    db_pass='test',
)
migrations = MigrationsCollection('./migrations')

with db.lock() as lock:
	history = db.history(lock)
	hooks, unapplied = migrations.to_apply(history)
	db.apply(lock, hooks, unapplied)
