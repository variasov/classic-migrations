# Спецификация classic-migrations — новая версия

> Статус: черновик спецификации (код не пишем, только описание).
> Текущая версия в репозитории: `setup.py` → `0.1b.0`, `__init__.py` → `8.2.0` (унаследовано от yoyo-migrations).
> Номер новой версии: **2.0.0** (major bump, т.к. изменения ломающие).

---

## 1. Цели

Упростить библиотеку: оставить только чистые SQL-миграции, заменить две
низкоуровневые функции (`read_migrations` + `get_backend`) одним классом
`Migrations`, сократить служебные таблицы с четырёх до одной, ввести
полноценные pre/post-хуки и контроль неизменности уже применённых миграций.

## 3. Детальное описание

### 3.1 Только SQL-миграции

- Миграция — это файл `*.sql` в каталоге источника миграций.
- Поддержка `*.py`-миграций удаляется полностью.
- Из публичного API удаляются: `step`, `group`, `transaction`, `StepCollector`,
  загрузка Python-модулей через `importlib`, `Migration.module` и всё, что
  связано с исполнением Python-кода миграций.
- Команда `new` всегда создаёт только `.sql`-файл; флаг `--sql` удаляется.

Сохраняемые возможности SQL-миграций:

- Директивы в начальном комментарии файла (парсятся как и сейчас):
  - `-- depends: <id> [<id> ...]` — зависимости;
  - `-- transactional: true|false` — выполнять ли в транзакции;
  - `-- comment: <текст>` — комментарий, попадающий в таблицу истории.
- Rollback-файл `<имя>.rollback.sql` (имя с вставкой `.rollback` перед
  расширением), как описано в README.

### 3.2 Единый класс `Migrations`

Вместо импорта двух функций:

```python
# было
from classic.migrations import read_migrations, get_backend
migrations = read_migrations("./migrations")
backend = get_backend("postgres://...")
backend.apply_migrations(backend.to_apply(migrations))
```

становится один класс:

```python
# стало
from classic.migrations import Migrations

m = Migrations(
    source="./migrations",
    database="postgres://...",
    migration_table="migrations",   # имя таблицы истории (опц.)
    schema=None,                    # схема таблицы (опц., см. §3.4)
)
m.apply()
```

Конструктор `Migrations`:

```python
Migrations(
    source: str | list[str] | None = None,   # каталог(и) миграций (fallback: Settings.SOURCE)
    database: str | None = None,             # URI подключения (fallback: Settings.DATABASE)
    migration_table: str = "migrations",     # имя таблицы истории
    schema: str | None = None,               # схема таблицы (fallback: Settings.MIGRATIONS_SCHEMA, §3.4)
)
```

Все параметры, не переданные явно, берутся из `Settings` (`.env` / переменных
окружения) — как сейчас.

Библиотека всегда работает в пакетном (batch) режиме: интерактивные вопросы
пользователю в терминале удалены (параметр `batch` и флаг CLI `--batch`
убраны).

Методы `Migrations` повторяют команды CLI (см. §4):

| Метод | Команда CLI | Назначение |
|-------|-------------|------------|
| `list()` | `list` | список миграций со статусом A/U |
| `apply(match=None, revision=None, all=False, force=False, one=False, check_hashes=True)` | `apply` | применить миграции |
| `develop(n=1, check_hashes=True)` | `develop` | применить без вопросов; если нет новых — переприменить последние N |
| `rollback(match=None, revision=None, all=False, force=False)` | `rollback` | откатить |
| `reapply(match=None, revision=None, force=False, check_hashes=True)` | `reapply` | откатить и применить заново |
| `mark(match=None, revision=None, all=False)` | `mark` | пометить применёнными без выполнения |
| `unmark(match=None, revision=None)` | `unmark` | снять отметку без отката |
| `new(message="")` | `new` | создать новый `.sql`-файл миграции |

Дополнительно (для внутренних нужд и удобства) допускается:
- `is_applied(migration_id)` — проверка статуса конкретной миграции.

`check_hashes=True` — включает сверку хешей применённых миграций (§3.5);
`check_hashes=False` временно отключает сверку (см. §3.5).

Сигнатуры методов могут уточняться при реализации; важно, что набор методов
соответствует набору команд CLI.

### 3.3 Разделение `Migrations` и CLI; бэкенды

- Вся бизнес-логика живёт в одном файле, например
  `classic/migrations/migrations.py` (класс `Migrations` + чтение/парсинг
  SQL-миграций + сверка хешей).
- Код CLI (argparse + функции-обработчики, вызывающие методы `Migrations`)
  размещается в отдельном файле `classic/migrations/cli.py`.
- Точка входа `migrations` (entry point) и `python -m classic.migrations`
  импортируют `main` из `cli.py`.

**Бэкенды.** Бэкенды для разных СУБД остаются **раздельными классами, каждый в
своём файле** (как сейчас — `backends/core/postgresql.py`, `backends/contrib/pymssql.py`
и т.д.), и каждый определяет свою специфику (SQL для создания таблицы истории,
нативный механизм блокировки, `paramstyle`, признак транзакционности DDL и
т.п.). Класс `Migrations` **сам выбирает нужный бэкенд под капотом** по схеме
URI подключения (`postgres://`, `mssql://`, `odbc://`, …) и не требует от
пользователя указывать бэкенд явно.

Все SQL-запросы определены **в каждом бэкенде отдельно**, с учётом его
диалекта и нативного `paramstyle` (создание таблицы истории, листинг таблиц,
выборка применённых миграций, `INSERT`/`DELETE` отметок, перенос из `versions`
и т.п.). В базовом классе `DatabaseBackend` **общих SQL-запросов нет** — только
общая оркестрация (управление соединением/транзакциями, проверка наличия
таблицы и вызов запросов бэкенда). Утилита конвертации параметров
(`change_param_style`) не используется.

Целевая структура пакета:

```
sources/classic/migrations/
    __init__.py          # публичный API: Migrations, исключения, __version__
    migrations.py        # класс Migrations + чтение/парсинг SQL + сверка хешей
    cli.py               # argparse + main() (отдельно от Migrations)
    connections.py       # парсинг URI, выбор класса бэкенда (внутренний)
    settings.py          # Settings (pydantic, .env)
    exceptions.py        # BadMigration, MigrationConflict, MigrationHashMismatch
    utils.py
    backends/            # base.py + по файлу на СУБД (postgresql, pymssql, odbc, …)
```

`__init__.py` экспортирует:

```python
__all__ = ["Migrations", "__version__"]
```

(`read_migrations`, `get_backend`, `step`, `group`, `transaction`, `ancestors`,
`descendants`, `default_migration_table` из публичного API убираются.)

### 3.4 Одна служебная таблица + настраиваемая схема

Сейчас создаются 4 объекта:
1. `versions` — таблица применённых миграций;
2. `history` — журнал операций (apply/rollback/mark/unmark, кто/когда);
3. `lock` — блокировка от параллельного запуска;
4. временная `migration_tmp_*` — проверка транзакционного DDL (создаётся и
   удаляется на лету).

В новой версии остаётся **одна таблица** — история применённых миграций:

```sql
CREATE TABLE {schema}.{migration_table} (
    migration_id VARCHAR(255) PRIMARY KEY,   -- имя миграции (имя файла без расширения)
    content_hash VARCHAR(64) NULL,           -- sha256 SQL-тела; NULL = сверка отключена (§3.5)
    applied_at   TIMESTAMP NOT NULL,         -- момент применения
    comment      VARCHAR(255) NULL           -- из директивы "-- comment:"
);
```

Изменения относительно текущей схемы:
- Убирается таблица `history` (журнал операций) — история операций больше не
  ведётся.
- Убирается таблица `lock` — блокировка переводится на нативные механизмы БД
  (см. «Блокировка» ниже).
- Вместо `migration_hash` (sha256 от `migration_id`) ключом становится
  `migration_id`, а отдельное поле `content_hash` хранит sha256 **тела**
  миграции для сверки (§3.5).
- Временная таблица `migration_tmp_*` убирается: проверка транзакционности DDL
  удаляется полностью (см. ниже).

**Настраиваемая схема.** Имя схемы для таблицы истории задаётся:
- параметром `schema=` конструктора `Migrations`;
- флагом CLI `--schema`;
- переменной окружения / `.env`: `MIGRATIONS_SCHEMA`.

Значение по умолчанию — **текущая схема соединения**, если драйвер её
поддерживает (PostgreSQL: `current_schema()`, MSSQL: `SCHEMA_NAME()` и т.п.);
иначе — `public`.

**Блокировка без таблицы.** Блокировка от параллельного запуска сохраняется,
но реализуется нативными (штатными) блокировками СУБД, которые автоматически
снимаются при закрытии соединения — в том числе при аварийном завершении
процесса миграций. Отдельная таблица `lock` не создаётся.

- PostgreSQL — session-скоп advisory-lock `pg_advisory_lock()/pg_advisory_unlock()`
  (либо блокировка строки таблицы истории на выделенном соединении,
  удерживаемая на время всего запуска);
- MSSQL — `sp_getapplock`/`sp_releaseapplock` в режиме сессии.

Ключевое требование: блокировка привязана к сессии/соединению, поэтому при
падении процесса БД сама отпускает её. Команда `break-lock` и метод
`break_lock()` удаляются — ручное снятие блокировки не требуется.

**Транзакционность DDL.** Проверка транзакционности DDL удаляется полностью:
переключение с одного типа БД на другой не предполагается, поэтому runtime-проверки
и временные таблицы не нужны. Выполнение миграции в транзакции определяется
директивой `-- transactional:` самой миграции (§3.1); бэкенд её не
переопределяет.

### 3.5 Контроль неизменности применённых миграций (сверка хеша)

Цель: гарантировать, что уже применённые миграции не были изменены задним
числом.

- Для каждого SQL-файла вычисляется `content_hash` = sha256 **тела** миграции
  (SQL-операторы после парсинга, без начального блока директив `-- depends:`/
  `-- transactional:`/`-- comment:` и без ведущего комментария). Правка только
  комментария не меняет хеш.
- При `apply` (и `develop`, `reapply`), перед выполнением, для каждой миграции,
  уже присутствующей в истории:
  - если `content_hash IS NULL` — проверка **не выполняется** (миграция была
    применена с отключённой сверкой);
  - если `content_hash IS NOT NULL` и не совпадает с вновь вычисленным —
    инструмент **отказывается применять** и сообщает список изменённых
    миграций (исключение `MigrationHashMismatch`).
- Новые миграции (отсутствующие в истории) применяются и записывают вычисленный
  `content_hash`.

Отключение сверки:
- Ключ `check_hashes=False` у методов `apply`/`develop`/`reapply` (CLI-флаг
  `--skip-hash-check`, см. §4) временно отключает сверку.
- Миграции, применённые с `check_hashes=False`, записываются в историю с
  `content_hash = NULL`; при последующих запусках они **не проверяются** (пока
  не будут переприменены через `reapply`).
- `mark` записывает вычисленный `content_hash` (миграция затем проверяется как
  обычно); `unmark`/`rollback` удаляют запись из истории.

### 3.6 Хуки pre/post-apply и pre/post-rollback

Сейчас есть только post-apply (класс `PostApplyHookMigration`, определяется по
префиксу имени файла `post-apply`, исполняется после применения).

Новые правила:
- Хук — это обычный SQL-файл в каталоге миграций со строго зарезервированным
  именем (опционально; отсутствие файла = нет хука):
  - `pre-apply.sql` — до применения набора миграций;
  - `post-apply.sql` — после применения набора миграций;
  - `pre-rollback.sql` — до отката набора миграций;
  - `post-rollback.sql` — после отката набора миграций.
- Хук не помечается в таблице истории (не является миграцией) и не участвует в
  сверке хешей.
- Порядок выполнения при `apply`:
  1. `pre-apply.sql`;
  2. миграции в топологическом порядке;
  3. `post-apply.sql`.
- Порядок выполнения при `rollback`:
  1. `pre-rollback.sql`;
  2. миграции в обратном порядке;
  3. `post-rollback.sql`.
- Хук выполняется каждый раз при вызове `apply`/`rollback`, даже если набор
  миграций пуст.
- Директивы `-- transactional:` у хуков учитываются так же, как у обычных
  миграций.

## 4. CLI

Список команд: `init`, `apply`, `develop`, `list`, `rollback`, `reapply`,
`mark`, `unmark`, `new`. Команда `break-lock` удалена (блокировка снимается
СУБД автоматически, см. §3.4).

Изменения аргументов:
- `new`: всегда SQL, флаг `--sql` удалён.
- Интерактивные вопросы удалены — CLI всегда работает в batch-режиме (флаг
  `--batch` удалён).
- Глобальный `--schema` (схема таблицы истории).
- `--migration-table` остаётся (имя таблицы истории).
- `apply`/`develop`/`reapply`: добавляется `--skip-hash-check` (отключить сверку
  хешей, §3.5).

## 5. Настройки (.env / переменные окружения)

Существующие (`SOURCE`, `DATABASE_*` и др.) сохраняются. `BATCH_MODE`,
`VERBOSITY`, `EDITOR`, `POST_CREATE_COMMAND`, `PREFIX` удаляются (не
используются). Библиотека всегда работает в batch-режиме (интерактивные вопросы
удалены). Добавляется/уточняется:

| Переменная | Назначение | Значение по умолчанию |
|-----------|------------|------------------------|
| `MIGRATION_TABLE` | имя таблицы истории | `migrations` |
| `MIGRATIONS_SCHEMA` | схема таблицы истории | текущая схема / `public` (§3.4) |

(`VERSION_TABLE` переименовывается в `MIGRATION_TABLE`; старый `VERSION_TABLE`
остаётся deprecated-алиасом.)

## 6. Обратная совместимость и миграция старых схем

- Это major-версия, обратная совместимость по API не гарантируется.
- При первом запуске с уже существующей БД, где есть старая таблица `versions`,
  выполняется **автоматическая миграция**: создаётся новая таблица истории и в
  неё переносится `migration_id`/`applied_at_utc` из `versions` (аналог текущего
  `_upgrade`). `content_hash` для перенесённых строк — `NULL` (старые миграции
  не проверяются до переприменения). Старые `history` и `lock` игнорируются.

## 7. Что удаляется (неполный список для реализации)

- `migrations.py`: классы/функции Python-миграций — `StepCollector`, `StepBase`,
  `MigrationStep`, `StepGroup`, `TransactionWrapper`, `Transactionless`,
  `step`, `group`, `transaction`, `_get_collector`, `importlib`-загрузка,
  `Migration.module`, ветка `not is_raw_sql()` в `Migration.load`.
- `migrations.py`: публичные `read_migrations`, `ancestors`, `descendants`,
  `heads`, `topological_sort` (переедут во внутренние при необходимости).
- `connections.py`: `get_backend` (логика переезжает в `Migrations`).
- `backends/base.py`: `history`/`log`-таблицы и все связанные SQL-константы и
  методы (`log_migration`, `get_log_data`, `_create_log_table`, `_upgrade` в
  части log), `lock`-таблица и `break_lock`/`break-lock`, динамическая проверка
  `_check_transactional_ddl` + `create_test_table_sql`, статический признак
  `supports_transactional_ddl`.
- `scripts/newmigration.py`: шаблон Python-миграции (`migration_template`) и флаг
  `--sql`.
- `migrations.py`: параметр `verbosity` конструктора; параметр `all` у
  `reapply`/`unmark`.
- `settings.py`: поля `VERBOSITY`, `EDITOR`, `POST_CREATE_COMMAND`, `PREFIX`.
- `exceptions.py`: `LockTimeout`.
- CLI: неиспользуемые флаги `--all`/`--force`/`--match`/`--revision` у команд,
  которым они не нужны (`develop`, `list`, `mark`, `unmark`, `reapply`).

## 8. Принятые решения (бывшие открытые вопросы)

1. **Блокировка** — решено: нативные блокировки СУБД, привязанные к сессии
   (авто-снятие при падении процесса); `break-lock` удаляется.
2. **История и хеш** — решено: хранить и `migration_id`, и `content_hash`
   (sha256 тела миграции); сверка при `apply`, отключение через
   `check_hashes=False` / `--skip-hash-check`; отключённые миграции — хеш `NULL`
   и не проверяются.
3. **Схема по умолчанию** — решено: текущая схема (если драйвер поддерживает),
   иначе `public`.
4. **Имя env-переменной схемы** — решено: `MIGRATIONS_SCHEMA`.
5. **Хуки** — решено: добавить `pre-rollback.sql`/`post-rollback.sql` в дополнение
   к `pre-apply.sql`/`post-apply.sql`.
6. **Флаг `--sql`** — решено: удалить (команда `new` всегда создаёт SQL).
7. **Старые таблицы** — решено: автоматический перенос из `versions` в новую
   таблицу истории.
8. **Транзакционность DDL** — решено: проверка удаляется полностью;
   переключение типа БД не предполагается, поэтому `supports_transactional_ddl`
   задаётся константой на уровне класса бэкенда (без runtime-проверок и
   временных таблиц).
9. **Номер версии** — решено: `2.0.0`.
